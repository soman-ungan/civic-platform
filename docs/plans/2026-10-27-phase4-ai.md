# フェーズ4（AI: モデレーション・自動タグ付け）実装計画と、フェーズ5（収集）の設計

## Context
フェーズ3（分析）が完了した。今のモデレーションは「全件承認」の仮実装（`backend/src/moderation.rs` の `Moderation::AutoApprove`）で、タグ付けの仕組みはない。フェーズ4で LLM による判定とタグ付けを入れる。あわせて、フェーズ5の行政資料の収集の設計を固める。

### 調査の結果（2026-10-26〜27）
- **会議録（ssp.kaigiroku.net）**: robots.txt は `/tenant/` の画面以外を不許可にしている（`Disallow: /`、`/tenant/js/` も不許可）。画面は JavaScript で不許可の範囲からデータを取る作りなので、**自動収集には大田原市議会事務局か提供元の許可（データ提供）が要る**。なお調査の際、`/tenant/js/` のスクリプト8件を1回ずつ取得してしまった（ユーザーに報告済み）
- **大田原市の予算書**（`/docs/2023051700017/`）: robots.txt では取得できる。R8 の予算書は 51.2MB、概要 3.61MB、家計簿 943KB（PDF）。ただし市の著作権方針は「著作権法上認められた場合を除き、無断で複製・転用できない」
- **総務省の決算カード**: 全市町村分が同じ形式（市町村分は H13〜R6 年度）。robots.txt は許可。政府標準利用規約（CC BY 4.0 互換）の適用は要確認
- **LLM の料金**（Anthropic 公開料金、2026-10-06 時点、100万トークンあたり）: Opus 5.5 $4 / $20、Sonnet 5.5 $2 / $10、Haiku 5.5 $0.10 / $0.50（入力10万トークン以下）。Batch API は半額。毎回同じ指示文はプロンプトキャッシュで安くなる

### ユーザーと決めたこと
1. **モデルは役割ごとに使い分ける**（評価用データで精度を測ってから確定する）
   - モデレーション = Claude Sonnet 5.5
   - 自動タグ付け = Claude Haiku 5.5
   - 行政資料の抽出（フェーズ5）= Claude Opus 5.5 を Batch API で
2. **フェーズ4 = AI（LLM の基盤・モデレーション・タグ付け）。収集は設計だけ行い、実装はフェーズ5**
3. **行政文書の原本は保持しない**。出典 URL・ハッシュ・ページ番号と、抽出結果（数値と短い引用）だけを残す
4. **会議録は許可を申請し、それまでは手動での取り込み**
5. **政治家（首長・議員）の名前はタグにしない**（2026-10-27）。選挙の際に参照できるよう、議会での発言や議決を議員ごとに検索できるようにはするが、それは「話題の分類」ではなく「出典（誰がいつ言ったか）」の情報として、フェーズ5で別の仕組み（公人の表 + 会議録の発言者の記載からの対応付け）として作る
   - 理由: タグは話題の分野と対象地域を表すもので役割が違う／名簿は改選のたびに変わる／AI に人物を推測させると発言の取り違え（名誉毀損のおそれ）が起こる／投票の対象の意見に議員名があると「誰の意見か」で賛否が決まり、党派的な分断を生む（ADR 0002 と同じ問題。Polis が投稿を匿名にするのは意見の中身で判断してもらうため）

## 方針
- 収集は「エージェント」にしない。パラメーターに従って取得する決まった手順のコードにし、LLM は取得済みの文書の抽出にだけ使う（robots.txt と利用規約を確実に守り、資料に紛れ込んだ指示に従わないため）
- Rust には公式 SDK がないので、Claude API は `reqwest`（MIT/Apache-2.0、rustls）で HTTP を直接呼ぶ。リクエストの形は claude-api スキルの cURL の例と `shared/` の文書に合わせ、実装時に確認する（`anthropic-version`、構造化出力 `output_config.format`、`stop_reason: "refusal"` の扱い、Batches）
- API キーが無い開発環境でも動くこと。キーが無ければ、モデレーションは今の自動承認、タグ付けは行わない
- テストは実際の API を呼ばない（偽の LLM で応答を差し替える）。実際の API を呼ぶのは評価のコマンドだけで、費用がかかるので実行の前にユーザーの了承を得る
- **投稿の文章を外部の AI に送ることを利用者に明示する**（投稿フォームに「投稿は公開前に AI で確認します」と書く）。AI に送るのは本文だけで、参加者の ID や関わり方は送らない（ADR 0002）

## Step 1: LLM の共通基盤 → `feat(backend): Claude API の共通基盤と使用量の記録を追加`
- `backend/src/llm/`
  - `client.rs`: Messages API の呼び出し。構造化出力、タイムアウト（15秒）、429・5xx の再試行、`stop_reason`（`refusal` / `max_tokens`）の判定
  - `Llm` enum: `Anthropic(client)` と、テスト用の `Fake(固定の応答)`。トレイトオブジェクトは使わない（`moderation.rs` と同じ流儀）
- 設定（`config.rs`、`.env.example`）
  - `ANTHROPIC_API_KEY`（任意）
  - `MODERATION_MODEL=claude-sonnet-5-5`、`TAGGING_MODEL=claude-haiku-5-5`
  - `LLM_DAILY_BUDGET_USD`（1日の上限。超えたら呼ばない）
- マイグレーション `llm_usage`: 用途、モデル、入力・出力・キャッシュのトークン数、推定費用、日時。上限の判定と、運用費の把握に使う
- テスト: 応答の解釈（正常、refusal、max_tokens、壊れた JSON）、予算の上限、キーが無いときの動き

## Step 2: モデレーション → `feat: LLM によるモデレーションを追加`
- `Moderation` に `Llm` を足す（`backend/src/moderation.rs`。今の `Verdict` の形をそのまま使う）
  - 判定の基準（システムプロンプト。キャッシュする）
    - **非公開**: 暴言、特定の個人への誹謗中傷・人格攻撃、差別、私人の個人情報（電話番号・住所・実名など）、脅迫
    - **公人（首長・議員など）**: 議会での発言、議決での賛否、政策や公務での行動への批判は**公開**する。人格攻撃、容姿や家族・私生活への言及、根拠を示さない犯罪の断定は**非公開**
    - **判定に迷う**: flagged
    - **主張の内容や政治的な立場では判断しない**（反対意見、行政への批判は公開する）
  - 出力（構造化出力）: `{verdict: approved|rejected|flagged, reason, suggestion}`。rejected のときは、穏やかな言い換えの例を `suggestion` に入れる（設計書 §4②）
  - 努力度（effort）は low
  - **refusal（安全上の理由で回答しない）は flagged として扱う**（人が確認する）
- 失敗時の扱い
  - タイムアウト・API のエラー・予算の超過のときは **pending のまま**にする（自動承認には戻さない）
  - バックグラウンドの処理（分析のワーカーと同じ形）で、pending の意見を再判定する
- 運営者の確認（認証のフェーズ6までは CLI）: `backend moderation list`（flagged と pending の一覧）、`approve <id>`、`reject <id>`
- 画面（`frontend/src/components/statement-form.tsx`）
  - 「投稿は公開前に AI で確認します」の注記
  - rejected のときの言い換えの提案（今の表示を使う）。pending・flagged のときは「確認のあと公開されます」（今の表示）
- テスト: 偽の LLM で approved / rejected（提案つき）/ flagged / refusal / タイムアウト → pending → 再判定で approved、の各経路。参加者 ID が LLM に送られないこと

## Step 3: 自動タグ付け → `feat: トピックの自動タグ付けを追加`
- **分野タグの共通語彙**を `data/seeds/020_field_tags.sql` に置く（全自治体共通のマスタ。例: 子育て、教育、福祉、医療・健康、防災・安全、交通、環境、農林業、観光、産業・雇用、財政、まちづくり、文化・スポーツ、行政運営）。語彙はユーザーに確認して確定する
- 地区タグは、そのトピックの自治体の `districts` から選ぶ（話題の対象地域で、人を分けるものではない。ADR 0002）
- 構造化出力のスキーマで、**選べるタグ（分野の語彙 + その自治体の地区）を enum で渡す**。語彙にないタグは付かない。分野は最大3、地区は最大2
  - **人物（首長・議員など）はタグにしない**。トピックの本文に議員名があっても、選べるのは語彙の中だけなので付かない（テストで確かめる）
- マイグレーションで `topic_tags.assigned_by`（'ai' / 'admin'）を追加する。AI による付け直しは、運営者が付けたタグを上書きしない
- 実行のタイミング: タグの無いトピックをバックグラウンドで処理する。手動では `backend tag [--topic <id>] [--force]`
- テスト: 偽の LLM で、語彙内のタグだけが付くこと、別の自治体の地区は選べないこと、運営者のタグを消さないこと

## Step 4: 評価用データと評価コマンド → `feat: モデレーションとタグ付けの評価を追加`
- `evals/moderation.jsonl`（50〜100件）、`evals/tagging.jsonl`（30件）。日本語で、**実在の人物名は使わない**（架空の名前）
  - 境界のケースを入れる: 強い批判だが正当な意見、皮肉、遠回しな中傷、個人情報らしきもの
  - **公人の境界のケース**（架空の首長・議員名で）: 議会での発言や議決への批判（公開）／人格攻撃・私生活への言及・根拠のない犯罪の断定（非公開）
- `backend eval moderation|tagging [--model <id>]`: 正解率、取り違えの内訳、1件あたりの費用と遅延を出す。**実際の API を呼ぶので、実行の前にユーザーの了承を得る**

## フェーズ5の設計（`docs/design/collection.md` に書く内容）
- **収集先のパラメーター化**: `collector_sources` の `adapter` と `config`（JSON）で表す。サイトの構成が変わっても、設定を直すだけで対応できるようにする
  - `html_link_list`: 一覧ページの URL、PDF のリンクを抜き出す正規表現、表示名から年度を読む正規表現、資料の種類。大田原市の予算書ページはこれで扱う
  - `soumu_settlement_card`: 団体コードだけで全市町村に共通
  - `manual_upload`: 許可を得て受け取った資料（会議録など）を運営者が取り込む
  - 会議録システムのアダプタ（kaigiroku など）: **書面の許可があるときだけ**有効にする
- **取得の共通処理**: robots.txt の確認、1サイトあたりの最低間隔（例: 5秒以上）、条件付き取得（ETag / Last-Modified）、連絡先つきの User-Agent。`config` に `terms_checked_at`・`terms_url`・`permission_ref` が無い収集先は動かさない（設計書の「収集前に robots.txt と利用規約を確認」を仕組みで守る）
- **変更の検知**: 文書のハッシュで新規・更新を判定する。一覧ページから資料が見つからなくなったら、運営者に通知する
- **抽出**: Opus 5.5 を Batch API で使う。PDF は文書として渡し、ページ番号つきの引用（citations）を使う。カードには数値・短い引用・出典（URL とページ）だけを載せる。原本は処理後に捨てる（`documents` テーブルに URL・ハッシュ・取得日時・ページ数だけを残す）
- **公人と発言者**
  - 公人の表（例: `public_officials`）: 氏名、役職（首長・議員など）、自治体、任期の開始・終了。改選・辞職・補選は任期で表し、過去の記録との対応を保つ
  - 発言と人物の対応は、**会議録の発言者の記載（「○3番（〇〇議員）」など）から機械的に決める**。LLM に人物を推測させない（取り違えは名誉毀損のおそれがある）。対応が取れない発言は人物に結び付けない
  - 記録には出典（会議名・日付・URL・ページ）を必ず付ける
  - トピックのカードでは「背景・出典」の欄に「〇〇議員（〇年〇月 定例会）」と引用つきで示す。**投票の対象になる意見（statements）の文には議員名を入れない**（意見の中身で判断してもらうため）
- **規模の見積もり（1自治体・1年あたり）**
  - ダウンロード: 約60MB（予算関係は約55MB、大田原市の実測。会議録は許可後に実測）
  - 保存: 1MB 未満（原本は保持しないため）
  - LLM: 入力約400万トークン（推定）。Opus 5.5 の Batch で約1,300円
  - 日々の更新確認: 一覧ページの条件付き取得だけで、数十KB
- **1サーバーで扱う自治体の数**: データ量も LLM の費用も小さい。制約になるのは、許可の取り付けとアダプタの保守という運営者の手間。「大田原市 → 栃木県内（同じシステムを使う自治体から）、1サーバーで50自治体程度まで」とし、それを超えたら PostgreSQL への移行と、収集処理の別サーバー化を検討する
- **公開の範囲**: 数値（事実）と短い引用、出典の明記。大田原市の情報政策課に、予算書から作ったカードの公開について確認する（運営者の作業）

## 実装時の変更点
- **`Llm` は enum ではなく構造体にした**: 1日の費用の上限を持たせるため、`Llm { backend, daily_budget_micro_usd }` とし、中の `Backend` を `Anthropic` / `Fake` の enum にした（トレイトオブジェクトは使わない方針は同じ）
- **TLS は rustls + ring**: reqwest の既定の TLS（rustls + aws-lc-rs）は、aws-lc に OpenSSL 系のライセンスが含まれ AGPL との両立が不確かなため、`rustls-no-provider` にして ring（Apache-2.0 AND ISC）を使う
- **HTTP の呼び出しのテスト**: 偽の LLM に加えて、手元に偽の Messages API を立て、ヘッダー・再試行・エラーの扱いを確かめるテストを足した
- **`statements.moderation_note` を追加**（計画に無かった）: AI の判定の理由を運営者が `moderation list` で見られるようにするため。API では返さない
- **`topics.tagged_at` を追加**（計画に無かった）: 当てはまるタグが無かったトピックを、バックグラウンドで繰り返し呼ばないようにするため
- **`moderation retry` を追加**: pending の再判定を手動でも行えるようにした
- **分野タグの語彙は `ON CONFLICT (id) DO UPDATE`**: 語彙の名前の変更（例: 防災 → 防災・安全）を既存の DB にも反映するため。開発用サンプルにあった分野タグは共通語彙に移した。（その後、ユーザーが決めた19分野に置き換えた）
- **評価を実行し、モデルを確定**: モデレーション60件・タグ付け40件で評価した（費用は約 0.13 ドル）。結果を見て、**タグ付けも Haiku 5.5 ではなく Sonnet 5.5 にした**（ユーザーが決定。ADR 0003）
- **分野タグの語彙はユーザーが決めた19分野にし、判断基準を定めた**（`docs/design/tagging-criteria.md`。各分野の定義は `tags.description`）
- **投稿のボタンの表示を「確認中…」にした**: AI の判定を待つ数秒の間の表示
