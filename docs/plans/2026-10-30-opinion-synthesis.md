# 意見の取りまとめ（類似判定の基盤・提言・第2回のトピック）

## Context
ADR 0005 は、トピックの統合を「提言」（合意点と意見が分かれた点を原文と数字のまま集める）と、それを元にした「第2回のトピック」で行うと決めているが、作り方は検討中だった。
似た意見・似たトピックの判定のしかた（ベクトル検索など）も「意見の取りまとめのフェーズで、トピックと意見の両方について決める」としていた。
今は候補を絞らず、AI に一覧を全部渡している（投稿の似た意見は承認済みの意見を新しい順に300件まで、会議録の取り込みの `same_as` は自治体のトピックを全部）。

## 決めたこと（2026-10-30 ユーザーと決定）
- **類似判定は2段階**: プログラムが候補を絞り、AI か運営者が判定する。候補は文字の2-gram の TF-IDF とコサイン類似度（依存を増やさず、API キーも費用も要らない）。トピックと意見で同じ基盤を使い、あとから埋め込みに差し替えられる形にする
  - 言い換え（別の語で同じ意味）には弱いので、件数が少ないうちは今どおり全部を AI に渡し、多いときだけ絞る
- **提言にできるのは締め切ったトピックだけ**（結果が固まっている）。分析の履歴とジャカード係数の判定は作らない。ほかに、分析の対象が5人以上、意見のグループが2つ以上
- **提言の木まで作る**: 提言は別の提言を子に持てる。まとめるときは子の見出し・前書きを使わず、子の項目（原文と数字）をたどって集める。循環は作れない
- 似たトピックの候補はプログラムが出し、まとめるかは運営者が決める（ADR 0005 の案の「AI が候補を出す」を改める）
- **意見が分かれた点のしきい値は 0.6 で仮置き**し、変えられるようにする（`.env`。作った提言に使った値を残し、画面に出す）
- **提言は3つ目のタブ**（トピック・提言・まちのお金）。使い心地を見て変えるかもしれない

## Part A 類似判定の基盤

### A1 `process/similarity.rs`（新規）
- 正規化（全角英数字→半角、小文字、記号・空白を除く）→ 文字の2-gram → コーパスの IDF → コサイン類似度
- `Index::build(docs: (id, text))`・`top_k(query, k)`（スコアつき）・しきい値を超える組をつないだ「まとまり」の候補
- トピックは「タイトル＋説明」、意見は本文。保存せずその場で計算する（数百件なので十分速い）
- テスト: 日本語の言い換え・同じ論点・別の論点の例

### A2 使う場所
- 投稿の似た意見（`process/moderation.rs`）: 承認済みが100件以下なら全部、超えたら似ている順の上位50件を AI に渡す（今は新しい順の300件）
- 会議録の取り込みの `same_as`（`ingest/minutes/extract.rs`）: 既存のトピックが100件を超えたら、その日の会議録に似ている順の100件に絞る
- 管理画面の下書き（議会・市民の提案）: 似ている既存のトピックを最大3件、スコアつきで出す
- CLI `list similar -m <slug> [--statements <topic>]`: 似ている組の一覧（費用 0。手元の DB で精度を確かめる）

## Part B 提言と第2回のトピック

### B1 マイグレーション
- `recommendations`（`id`・`municipality_id`・`title`・`preface`・`status`（draft / published）・`divided_threshold`・`created_at`・`published_at`）
- `recommendation_topics`（直接の元のトピック）・`recommendation_children`（子の提言）
- `recommendation_items`: 作ったときの原文と数字の写し（種類（合意点 / 分かれた点）・元のトピック・意見 ID・本文・参加した人数・全体の賛成/反対/パス・グループごとの賛成と反対の割合（JSON）・並び順）
- `recommendation_residency`: 元のトピックごとの関わり方の内訳（二次秘匿してから保存）
- `topics.recommendation_id`: 第2回のトピックの元の提言
  - `source_type` の CHECK は変えない（SQLite では作り直しが要る）。第2回は元のトピックの `source_type` を受け継ぎ、混ざっていれば `assembly`。画面は `recommendation_id` で「第2回」を出す

### B2 中身を作る（`process/recommendation.rs`・`records/recommendations.rs`）
- 合意点: 今のピン留めと同じ（全グループで (A+1)/(S+2) ≥ 0.8）
- 意見が分かれた点: あるグループで (A+1)/(S+2) ≥ しきい値、かつ別のグループで (D+1)/(S+2) ≥ しきい値。5人未満のグループは数えない
- 項目はプログラムだけで決める（運営者も足し引きしない）
- 子の提言は公開済みだけ。自分の祖先は子にできない。公開した提言は変えない
- 見出しと前書きは AI が下書き（送るのは項目の原文と元のトピックの題だけ。氏名はプログラムで確かめる。中立に）。キーが無い・失敗したら運営者が書く

### B3 運営者の操作（CLI と管理画面。中身は同じ関数）
- 締め切ったトピックのまとまりの候補（同じ分野タグ＋類似度）。候補から選ぶか、自分で選ぶ
- 提言の下書きを作る → 見出しと前書きを確かめる・直す → 公開
- 公開した提言から第2回のトピックの下書きを作る（合意点と分かれた点の原文を最初の意見に。多すぎれば運営者が下書きで減らす）
- CLI: `add recommendation`・`show recommendation`・`publish recommendation`・`add topic --from-recommendation`

### B4 画面と API
- `/{slug}/recommendations`（一覧）・`/{slug}/recommendations/{id}`（詳細: 合意点・分かれた点・数字・関わり方の内訳・元のトピックと子の提言へのリンク・印刷/PDF）
- タブを「トピック・提言・まちのお金」に
- 締め切ったトピックと第2回のトピックに、関係する提言へのリンク
- 下書きの提言は運営者の API 以外に出さない

### B5 サンプルとテスト
- `generate_sample_votes.py` で締め切ったサンプルのトピックを足す
- テスト: 合意点・分かれた点の判定、2自治体を混ぜない、締め切っていないトピックは選べない、循環を作れない、子をたどって集める、作った時点の数字が残る、下書きが外に出ない、氏名の確かめ、第2回の最初の意見
