# トピックマップと市民のまとめ（運営者の提言を置き換える）

## Context
意見の取りまとめ（`2026-10-30-opinion-synthesis.md`）の Part B で、運営者が作る「提言」を作った（PR #29、未マージ）。
その後ユーザーと見直し、締め切ったトピックを市民が地図で総覧し、似たトピックを選んで、自分で次のトピックを提案する形に一本化する（2026-10-30）。
類似判定の基盤（Part A、PR #28）はそのまま使う。

## 決めたこと（2026-10-30 ユーザーと決定）
- **トピックマップ**: トピック1件をドット1つにし、トピックどうしの類似度で配置する。表示はタグ（分野）で絞ったものだけ。配置は PCA（類似度の表の各行を特徴として、今の `powerit_pca` で2次元に。多次元尺度構成法とほぼ同じ）。力学モデルは使わない（決定的で、今の数理を使え、意見マップと同じ考え方になるため）
  - どれとも似ていないトピックは中央付近に出る。軸の向きは決まった規則でそろえる（地図が裏返らないように）
- **市民のまとめに一本化**: 運営者の提言（PR #29 の提言のテーブル・API・CLI・管理画面のタブ・AI の見出し）はやめる
  - 起点のトピックを選ぶと、その近傍（起点との類似度が目安以上）だけを追加で選べる
  - 集約ページで、選んだトピックごとの合意点・意見が分かれた点・グループごとの代表的な意見を見られる（印刷できる）
  - 市民はそれを見ながら、自分で新しいトピックを書いて提案する（「この意見を使う」で原文を最初の意見に写せる）。提案は今の市民提案と同じ（週1件に数える・最初の意見1〜10件・運営者の確認・公開待ち）。元のトピック（親）をツリーとして記録する
- **AI は使わない**: 論点の自動まとめはしない（ADR 0004「AI に新しい選択肢を作らせない」・ADR 0005 の「中身はプログラムで決める」）。グループを AI で要約することもしない（人をひとくくりに名付けることになり、ADR 0002「分断を生まない」とぶつかる。Polis と同じく代表的な意見で示す）。地図・近傍・まとめはすべて類似度と分析の計算だけで、API の費用はかからない
- 近傍は起点との類似度で決める（選んだどれかの近傍にすると、選ぶたびに範囲が広がるため）

## やること

### Step 1 トピックマップ（backend）
- `process/topic_map.rs`: 自治体の締め切ったトピックのうち、タグの付いたものの「タイトル＋説明」の類似度の表 → PCA で座標。軸の向きをそろえる
- `GET /api/municipalities/{slug}/topic-map?tag=`: 点（id・題・座標・分析の対象の人数・締め切った日）と、似ている組（目安以上）。タグの一覧（締め切ったトピックに付いているもの）も返す
- 締め切ったトピックは変わらないので、その場で計算する（100件で十分速い）。遅ければ保存に切り替える

### Step 2 集約ページ（backend）
- `GET /api/municipalities/{slug}/digest?anchor=&topics=`: 起点と、起点の近傍のトピックだけ（近傍に無いもの・締め切っていないもの・別の自治体のものは 422）。トピックごとに合意点・意見が分かれた点（PR #29 の計算）・グループごとの代表的な意見（分析の repness）・分析の対象の人数・関わり方の内訳（二次秘匿済み）
- 分析の対象が5人未満のトピックは、合意点などを出さない（今の分析の公表の決まりと同じ）

### Step 3 提案に親を付ける（backend）
- マイグレーション `topic_parents`（`topic_id` → `parent_id`）
- 提案の API に `parent_ids`（任意）。あれば、起点（最初の1件）の近傍の締め切ったトピックだけかをプログラムで確かめる。週1件・意見1〜10件・運営者の確認は今と同じ
- トピックの詳細に `parents`（元のトピック）・`children`（ここから生まれた公開済みのトピック）。管理画面の下書きにも元のトピックを出す

### Step 4 画面（frontend）
- タブを「トピック・これまでの議論・まちのお金」に（名前は仮）
- タグを選ぶとマップ（SVG。新しい npm パッケージは使わない）。点を押すと起点になり、近傍が強調され、近傍の点だけを追加で選べる。選んだものの一覧と「まとめを見る」
- 集約ページ `/{slug}/digest?anchor=…&topics=…`（印刷できる）。「このまとめから新しいトピックを提案する」で提案のフォームへ（親と、「この意見を使う」で選んだ原文を渡す）
- トピックの画面に、元のトピックとここから生まれたトピック

### Step 5 PR #29 の作り直し
- 外す: 提言のテーブル・`records/recommendations`・提言の API・CLI・管理画面のタブ・AI の見出し・`RECOMMENDATION_DIVIDED_THRESHOLD`・`llm_usage` の作り直し
- 残す: 合意点・分かれた点の計算（しきい値は定数 0.6 で仮置き。変えやすく1か所に）、公表の決まりの移動（`process/analysis/disclosure.rs`）、締め切ったサンプル
- マイグレーションは main に入っていないので、このブランチで書き換える

### Step 6 テストと docs
- テスト: 配置が決定的で向きがそろう、タグで絞る、近傍の外は選べない、2自治体を混ぜない、5人未満は中身を出さない、提案の親（近傍・締め切り・週1件）、親子のリンクは公開済みだけ、下書きは出さない
- ADR 0005 の「提言」を「市民のまとめ」に書き直す（AI で整理しない・グループを AI で要約しない理由も）。api・schema・cli・data-flow・overview・CLAUDE.md・`plans/README.md`。`2026-10-30-opinion-synthesis.md` の Part B はこの計画に置き換えた旨を、その計画の末尾に追記する

## 実装時の変更点
- 地図の配置の座標と線の度合いは、小数4桁に丸めて返す。似ている度合いの計算は、足し算の順を固定した（2-gram の数え上げを BTreeMap に）。同じ入力で、座標が最後の桁まで同じになるように
- 地図はタグを選ばないとタグの一覧だけを返す。画面は、締め切ったトピックの多いタグを最初に開く
- 地図のタブ（`/{slug}/map`）は、横フリックでタブを変えない（地図に触れて操作するため）
- まとめから提案のページへは、URL で元のトピックと「使う」を押した意見の ID を渡し、提案のページがまとめを読み直して原文をフォームに入れる（保存しない）
- 運営者の下書きのカードに、元のトピックと「一方の立場に寄せて書き換えていないか」の注意を出す
- 新しいマイグレーションは `20261030130000_create_topic_parents.sql`。前の案のマイグレーション（`20261030120000_create_recommendations.sql`）は main に入っていないので消した。前の案のブランチで起動した手元の DB は、そのままでは起動できない（sqlx が「当てたマイグレーションが無い」と止める）。次で戻す（llm_usage はそのまま）:
  ```sql
  BEGIN;
  DROP TABLE recommendation_items;
  DROP TABLE recommendation_children;
  DROP TABLE recommendation_topics;
  ALTER TABLE topics DROP COLUMN recommendation_id;
  DROP TABLE recommendations;
  DELETE FROM _sqlx_migrations WHERE version = 20261030120000;
  COMMIT;
  ```
- 確かめ: `cargo test`（新しいテストを含め、すべて通る）・clippy・frontend の lint と型チェック。手元の DB の写しを上のとおり戻し、`seed --dev` して、地図・まとめ・近傍の外の 422・提案のページ（まとめからの引き継ぎ）を開発サーバーで確かめた。提案のフォームに原文が入るところは、パスキーが要るのでブラウザでは確かめていない（提案の API の親は統合テストで確かめた）
