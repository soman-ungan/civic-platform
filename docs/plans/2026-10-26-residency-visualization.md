# 居住属性の可視化と、「分断を生まない」属性の扱いの原則

## Context
ユーザーから「住民と関係人口の違い」を可視化したいという要望があった。表示方法と、性別・年齢などの観点も扱うべきかを検討する中で、ユーザーと次の認識に至った。

> 市民を**本人の属性（年齢・性別など）や市内の地区（黒羽・湯津上・旧大田原市街）**で分けて見せることと、**その自治体との関わり方（住民・周辺・通勤通学・関係人口）**で分けて見せることは、分断への影響が本質的に異なる。前者は「〇〇の人たちはこう考える」という対立の構図を作り、分断を煽る。Polis の本質（意見グループは意見だけで作り、立場を超えた合意点を見つける）に反する。

決まったこと:
- **年齢・性別を必須で集める属性にする案は棄却する。** 任意で集めることも当面は行わない（行うなら、新しい ADR で目的と使い方を決めてから）
- **市内の地区ごとに属性を分け、可視化することはしない。** 地区は集めない
- **自治体との関わり方（residency_type）の可視化は今着手する**（frontend 中心）。意見マップには「① グループの構成」を重ねる。各意見グループに、どの関わり方の人がいるかを示す（Polis のレポートにある「各グループの属性の内訳」と同じ考え方）

あわせて、既存の表示の問題も直す。5人未満の区分を隠すルールが、引き算で破られる（隠した区分が1つだけだと合計から逆算できる。投票には居住属性の登録が必須なので、意見ごとの投票者数は「グループごとの特徴」の表から分かる）。

## 二次秘匿のルール
1. 5人未満の区分を隠す（今と同じ）
2. 隠した区分の合計が 1〜4 人になるときは、見えている区分のうち最も人数の少ないものも隠す。合計が5人以上になるか、すべて隠れるまで繰り返す
3. 実装は `backend/src/routes/analysis.rs` の関数 `suppress` 1つにまとめ、グループの構成と意見ごとの集計の両方から使う

## Step 1: 地区を集めない → `feat: 参加者の地区を集めないようにする`
- **backend**: `PUT /relation` の入力から `district_id` を外す（送られてきても無視する。serde の既定の挙動）。保存は常に NULL
  - テスト: 地区を送っても保存されないことを確かめる。別の自治体の地区を指す関係を DB で防ぐ制約のテスト（`tests/schema.rs`）は、スキーマが残る限りそのまま
- **新しいマイグレーション** `clear_relation_districts`: `UPDATE user_municipality_relations SET district_id = NULL`（すでに入っている地区を消す。開発用のデータのみ）。列はマージ済みのマイグレーションを書き換えないルールに従って残し、将来削除する候補として ADR に記録する
- **frontend**: `relation-sheet.tsx` から地区の選択欄を外し、`districts` を受け渡していた props も整理する（`voting-panel.tsx`、`topic-interaction.tsx`、トピック詳細のページ）
- **開発用サンプル**: `scripts/generate_sample_votes.py` で住民に地区を付けるのをやめ、`data/dev-seeds/110_*.sql` を生成し直す
- **トピックの地区タグ（#黒羽 など）は残す**。人を分けるものではなく、話題の対象地域を示すものなので

## Step 2: backend の集計 → `feat(backend): 意見グループの関わり方の構成と、二次秘匿を追加`
- 分析 API に `group_composition: [{group_id, by_type: {resident|neighbor|commuter|related: 人数 or null}}]` を追加する
  - グループのメンバーは保存済みの状態（`ConvState.base_clusters`）から集め、その自治体の `user_municipality_relations` と突き合わせる
  - 二次秘匿を適用する。隠した区分の合計は返さない（frontend で「グループの人数 − 見えている合計」として出す。5人以上か0になる）
- 既存の `residency`（意見ごとの区分別の賛成数）にも二次秘匿を適用する
- テスト: 構成の人数、参加者 ID が含まれないこと、隠した区分の合計が1〜4人のとき次に小さい区分も隠れること。既存の居住属性のテストは二次秘匿の後の期待値に直す

## Step 3: frontend の可視化 → `feat(frontend): グループの構成と、関わり方ごとの違いをドット図で表示`
書く前に dataviz スキルを読み込み、色・凡例・アクセシビリティの指針に従う。
- **`group-composition.tsx`（新規）**: 意見マップのすぐ下に「グループの構成（このまちとの関わり方）」を置く
  - グループごとに1本の100%積み上げ帯を描く（グループの色と紛れない別の配色）
  - 隠した分は灰色の「5人未満の区分」にまとめる
  - 割合を文字でも出し、「参加者の中での内訳です（無作為の標本ではありません）」と注記する
- **`residency-dot-plot.tsx`（新規）**: `analysis-panel.tsx` の `ResidencyTable` を置き換える
  - 意見ごとに 0〜100% の軸を引き、関わり方ごとの賛成率を色と形の違う点で置き、最大と最小を線で結ぶ
  - 差の大きい順に5件。隠した区分は点を描かず「—（5人未満）」と出す
  - 見出しは「このまちとの関わり方による違い」にする（「住民と関係人口の違い」より、4区分すべてを指すことが伝わる）
- `types.ts` に `group_composition` の型を追加する

## Step 4: ドキュメント → `docs: 分断を生まない属性の扱いを ADR と設計書に記録`
- **`docs/adr/0002-participant-attributes.md`（新規）**
  - 原則: 市民を本人の属性（年齢・性別など）や市内の地区で分けて見せない。分けて見せてよいのは、自治体との関わり方（residency_type）だけ。理由は上の Context（この対話で至った認識）
  - 決定: 年齢・性別の必須収集は棄却。任意収集も当面は行わない（行うなら新しい ADR で決める）。地区は集めない。`users.age_group / gender / occupation` と `user_municipality_relations.district_id` は使わず、将来削除する候補
  - 関わり方の扱い: クラスタリングには使わず、グループの説明と意見ごとの比較にだけ使う（Polis の原則。Polis はメタ意見による自己申告で属性を集め、クラスタリングから除外し、レポートでグループの内訳として示す。リポジトリで確認）
  - 公表のルール: 最小人数5人と二次秘匿。「参加者の中での傾向」と明記する
  - 地区タグ（話題の対象地域）は人を分けないので残す
- **`docs/grand-design.md`**
  - §3⑤ users: 年代・性別・職業の項目と「クラスター分析に活用」を、ADR 0002 の方針（集めない）に書き直す
  - §3⑥: `district_id` を「集めない（分断を避けるため。ADR 0002）」に書き直す
  - §4④: 関わり方の比較はグループの説明として行うこと、地区や本人の属性では比較しないことを明記する
- **CLAUDE.md**: 「多自治体対応の原則」の近くに、「分断を生まない」原則（ADR 0002）を1項目追加する。API の一覧に `group_composition` と二次秘匿を追記する
- **メモリ**: 属性や区分で集計・可視化する機能を考えるときは ADR 0002 を先に確認すること（ユーザーの指摘による方針）
