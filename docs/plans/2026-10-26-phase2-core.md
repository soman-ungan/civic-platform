# フェーズ2（コア）実装計画

## Context
フェーズ1（土台・多自治体スキーマ・seed・ライセンス・フッター）と Docker 方針の ADR が完了した。フェーズ2では、市民が実際に意見へ投票できる Polis のコア体験を作る。範囲は CLAUDE.md のとおり。
- 自治体別のトピック一覧・詳細
- ステートメント投稿
- 投票 API
- Polis 風の投票 UI
- 開始時に PostgreSQL 互換の CI（ADR 0001）

ユーザーと決めたこと:
- **ユーザーの識別**: 匿名参加者の Cookie。初めて書き込むときに匿名の `users` 行を作り、署名付きの HttpOnly Cookie で識別する。フェーズ6でこのユーザーを SNS アカウントに紐づける。
- **モデレーション**: 差し替えられる自動承認。保存時は `pending` → モデレーターを通す → 結果を反映、という流れを今作り、判定の中身だけ「全件 approved」の仮実装にする。フェーズ4で AI 判定に差し替える。
- **居住地属性**: フェーズ2に含める。その自治体で初めて投票するときに1回だけ聞く。

完了時の状態: `/otawara` でトピック一覧を見て、詳細画面でカードを1枚ずつ「賛成 / 反対 / パス」で判定でき、自分の意見も追加できる。投稿者の情報はどの API レスポンスにも含まれない。

## 進め方
- **実装前に、この計画を `docs/plans/2026-10-26-phase2-core.md` として保存する**（ユーザーの方針: 承認された計画は、実装を始める前に docs に記録する）。`feat/phase2` の最初のコミット `docs: フェーズ2の実装計画を追加` にする。この方針は CLAUDE.md の「開発ルール」とメモリにも書いておく
- `main` から `feat/phase2` ブランチを切り、下のステップごとにコミットする。最後に PR を作り、Step 0 の CI が通ることを確認してからマージする。
- 新しく追加する依存（すべて MIT または MIT/Apache-2.0。追加時に確認する）:
  - `uuid`（`v7`, `serde`）— ID の生成
  - `chrono` — ISO8601（UTC）の日時文字列を作る
  - `thiserror` — API エラー型の定義
  - `axum-extra`（`cookie-signed`, `cookie-key-expansion`）— 署名付き Cookie
  - frontend に新しい依存は入れない

## Step 0: CI と PostgreSQL 互換チェック → `ci: GitHub Actions で検査と PostgreSQL 互換チェックを追加`
`.github/workflows/ci.yml`（push と PR で実行）に3つのジョブを置く。
- **backend**: `cargo fmt --check` / `cargo clippy --all-targets -- -D warnings` / `cargo test`。cargo のキャッシュあり
- **frontend**: `npm ci` / `lint` / `typecheck` / `build`
  - `NEXT_PUBLIC_SOURCE_URL` は `${{ github.server_url }}/${{ github.repository }}` を渡す（本番ビルドでは必須のため）
- **postgres-compat**: `postgres:17` をサービスコンテナで起動し、`psql -v ON_ERROR_STOP=1 --single-transaction` で流す
  - 流すもの: `backend/migrations/*.sql` → `data/seeds/*.sql` → seed をもう一度（冪等性の確認）
  - sqlx-cli はインストールに時間がかかるので使わない
- 確認: push して `gh run watch` で3ジョブとも成功すること。PG 側で失敗した場合は SQL を直す（ここが ADR で「未検証」としていた部分）

## Step 1: API の土台 → `feat(backend): API の共通基盤と匿名参加者 Cookie を追加`
- **ルーティング**: すべて `/api` の下に置く（ADR のとおり、Caddy では `/api` をそのまま backend に渡すため）。`/health` は `/api/health` に移し、`tests/health.rs` と CLAUDE.md を直す
- **`src/error.rs`**:
  - `ApiError`（`NotFound` / `Validation` / `Conflict` / `Internal`）→ `{"error": {"code": "...", "message": "..."}}`
  - sqlx のエラーはログに出し、クライアントには `internal` とだけ返す
- **`src/util.rs`**: `new_id()`（UUID v7）、`now_iso()`（`2026-10-26T12:34:56.789Z` 形式）
- **`src/participant.rs`**: 匿名参加者のエクストラクター
  - `Participant`（書き込み用）: Cookie `cp_uid` が有効ならその user を使い、無ければ `users` に匿名ユーザーを作って Cookie を返す
  - `MaybeParticipant`（読み取り用）: ユーザーを作らない
  - Cookie の属性: HttpOnly、SameSite=Lax、Path=/、有効期限1年。`COOKIE_SECURE=true` のときだけ Secure を付ける（本番用）
  - 改ざんされた Cookie や、存在しないユーザーを指す Cookie は「無いもの」として扱う
  - CSRF 対策: SameSite=Lax と、書き込み API は JSON のみ受け付ける（axum の `Json` は Content-Type を検査する）ことの2点で防ぐ
- **`config.rs`**: `SESSION_SECRET`（必須、32バイト以上）と `COOKIE_SECURE` を追加
  - `SESSION_SECRET` は未設定なら起動時にエラーにする。既定値は置かない
  - `.env.example` には空欄と生成コマンド（`openssl rand -hex 32`）を書く
- **クエリの書き方**: 実行時の `sqlx::query_as` + `#[derive(FromRow)]` を続けて使う。プレースホルダーは `$1` 形式（sqlx は SQLite でも受け付け、PG とそのまま共通になる）。`query!` マクロは PG 移行の時に改めて検討する

## Step 2: 自治体・トピックの読み取り API → `feat(backend): 自治体とトピックの API を追加`
`src/routes/municipalities.rs` と `src/routes/topics.rs`。
- `GET /api/municipalities` → 有効な自治体のみ `[{id, slug, name, prefecture_name}]`
- `GET /api/municipalities/{slug}` → 自治体と地区の一覧。無効な自治体と存在しない slug は 404
- `GET /api/municipalities/{slug}/topics?tag={tag_id}` → 新しい順。各トピックには次を付ける
  - タグ `[{id, kind, name}]`
  - 承認済みの意見数と投票者数
- `GET /api/municipalities/{slug}/topics/{topic_id}` → 詳細
  - **トピックが別の自治体のものなら 404**（`WHERE t.id = $1 AND t.municipality_id = $2`）
- すべてのクエリで、slug から求めた `municipality_id` で絞り込む（CLAUDE.md の原則）

## Step 3: 投票・意見投稿・居住地属性の API → `feat(backend): 投票・意見投稿・居住地属性の API を追加`
- **`PUT /api/municipalities/{slug}/relation`** `{residency_type, district_id?}` → `user_municipality_relations` を upsert する
  - 別の自治体の地区を指定したら 422（DB の複合外部キーでも防がれる）
- **`GET .../topics/{id}/next-statement`** → `{statement: {id, body} | null, progress: {voted, total}, needs_relation: bool}`
  - 対象は、承認済みで、その人がまだ投票していない意見
  - 並びは `ORDER BY random()`（SQLite と PG の両方にある関数）
  - Cookie が無い人は「未投票・`needs_relation: true`」として扱う
- **`POST .../statements/{sid}/votes`** `{value: 1 | -1 | 0}`
  - 居住地属性が未登録なら 409 `relation_required`
  - その意見が、その自治体のそのトピックの承認済みの意見でなければ 404
  - `ON CONFLICT (user_id, statement_id) DO UPDATE` で、最後の判断を記録する（二度押しや再送でも安全）
- **`POST .../topics/{id}/statements`** `{body}`
  - 前後の空白を除き、1〜140**文字**（`chars().count()`、DB の `length()` と同じ数え方）でなければ 422
  - `pending` で保存 → `Moderation::review(body)` → status を更新 → `{id, status}` を返す
- **`src/moderation.rs`**:
  - `enum Moderation { AutoApprove }` と `async fn review(&self, body) -> Verdict`
  - `Verdict` は Approved / Rejected{suggestion} / Flagged
  - フェーズ4で AI の分岐を足すだけにする。トレイトオブジェクトや async-trait のクレートは使わない
- **匿名性**: 意見のレスポンス型には `user_id` のフィールドを持たせない（型の段階で出せない）

## Step 4: 開発用サンプルデータ → `feat(db): 開発用サンプルデータと seed --dev を追加`
- `data/dev-seeds/` に大田原市用のサンプルを置く
  - 内容: トピック3件、各トピックに意見5〜8件（`user_id` NULL のシード意見、approved）、分野タグと地区タグ
  - タイトルには必ず「【サンプル】」を付ける。実際の議案と誤解されないように、架空の内容だと分かる書き方にする
- `backend seed --dev` は `data/seeds/` → `data/dev-seeds/` の順に流す。引数なしの `backend seed` は本番用で、`data/seeds/` だけを流す
- `seed::run` はそのまま使い、ディレクトリを2回渡すだけにする（`backend/src/seed.rs`）

## Step 5: フロントエンド → `feat(frontend): トピック一覧と Polis 風投票画面を追加`
書く前に `node_modules/next/dist/docs/` で確認する（AGENTS.md）。確認するのは、Cache Components で fetch を Suspense で囲むこと、`params` / `searchParams` が Promise であること、`redirect` / `notFound`、rewrites の4点。
- **API の経路**:
  - ブラウザからは同じオリジンの `/api/*` を呼ぶ。開発時は `next.config.ts` の rewrites で `API_INTERNAL_URL`（サーバー側だけの変数、既定 `http://127.0.0.1:8080`）へ転送する。本番では Caddy が振り分ける
  - これで `NEXT_PUBLIC_API_BASE_URL` は不要になるので `.env.example` から消し、`API_INTERNAL_URL` を足す
- `src/lib/api.ts`（サーバー側の fetch ヘルパー）、`src/lib/types.ts`（API のレスポンス型）

- `app/[municipality]/topics/[id]/page.tsx`: トピックの概要（Server Component）と、投票カード（Client Component）
- `src/components/voting-card.tsx`（`"use client"`）:

- `src/components/relation-sheet.tsx`: 初回の投票前にボトムシートを出す。選択肢は「住民 / 周辺住民 / 通勤・通学 / 関係人口」と、任意の地区（その自治体の districts から選ぶ）

## 実装時の変更点

計画から外れた点と、その理由。

- **CI を Draft PR で先に回した**: ワークフローの起動条件が「`main` への push と PR」なので、ブランチを push しただけでは動かない。最後に作る予定だった PR を、Draft として最初に作った（#1）。あわせて `actions/checkout` / `setup-node` を v7 に上げた（Node 20 の非推奨警告への対応）。
- **トピック一覧のレスポンス**: 配列ではなく `{topics, tags}` にした。`tags` は絞り込み前の全件で、チップの表示に使う。
- **投票のステータスコード**: 計画では 201 としていたが、新規か上書きかを区別するためだけにクエリを増やす価値がないので、常に 200 を返す。
- **匿名参加者を作るタイミング**: 計画では、書き込み API の受付時（エクストラクター）に作る想定だった。そのままだと、不正なリクエストや属性未登録の投票のたびに、使われない `users` 行が増えてしまう。`MaybeParticipant` で受け取り、入力の検証が済んでから `Participant::ensure` で作るように変えた。投票は属性の登録が前提なので、参加者を作らずに 409 を返す。
- **`cookie` クレートを直接の依存に追加**: Cookie の有効期限の指定に `cookie::time` が必要なため（既存の間接依存と同じ 0.18。MIT/Apache-2.0）。
- **トップの自動遷移は proxy で行う**: Cache Components では、Suspense の内側で `redirect` すると meta タグによるブラウザ側の移動になり、読み込み画面が一瞬見える。そこで `src/proxy.ts`（`/` のみが対象）でサーバー側から 307 を返すようにした。
- **タグの絞り込みはクライアント側で行う**: 設計書の「タップで瞬間フィルター」に合わせ、取得済みの一覧をその場で絞り込み、`history.replaceState` で `?tag=` を更新する。API の `?tag=` もそのまま残している。
- **Next 16 の仕様**: `error.tsx` が受け取るのは `reset` ではなく `retry`、`error` の型は `unknown` だった（同梱ドキュメントで確認）。
- **スマホ実機・ブラウザでの表示確認は未実施**: この環境にブラウザがないため。HTML と API の通しの流れは curl で確認した。
