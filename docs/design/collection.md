# 行政資料の収集の設計（フェーズ5）

- 状態: 設計（実装はフェーズ5）
- 日付: 2026-10-27
- 計画: `docs/plans/2026-10-27-phase4-ai.md`（フェーズ5の設計）
- 関連: 設計書 §3⑪ `collector_sources`、§4①

## 方針

1. **収集は「エージェント」にしない。** 設定（パラメーター）に従って取得する、決まった手順のコードにする。LLM は、取得済みの文書からの抽出にだけ使う
   - robots.txt と利用規約を確実に守るため（LLM に URL を選ばせると、許可の無い範囲に行くおそれがある）
   - 資料に紛れ込んだ指示に従わないため
2. **行政文書の原本は保持しない。** 出典（URL・ハッシュ・ページ番号・取得日時）と抽出結果（数値と短い引用）だけを残す
3. **許可と規約の確認が記録されていない収集先は動かさない。** 設計書の「収集前に robots.txt と利用規約を確認する」を、運用の注意ではなく仕組みで守る
4. **自治体・サイトごとの違いは、アダプタと設定（`collector_sources.config`）に閉じ込める。** サイトの構成が変わっても、多くは設定を直すだけで対応できるようにする

## 調査の結果（2026-10-26〜27、大田原市）

| 資料 | 場所 | robots.txt | 利用規約など | 扱い |

| 会議録 | `https://ssp.kaigiroku.net/tenant/ohtawara/pg/index.html` | `/tenant/` の画面以外は不許可。画面は JavaScript で不許可の範囲からデータを取る | — | **自動収集には許可が要る。** 許可を申請し（`docs/outreach/minutes-data-request.md`）、それまでは手動で取り込む |

## 収集先の設定（パラメーター化）

`collector_sources` の1行が1つの収集先になる。`adapter` で取得の方法を、`config`（JSON）でその自治体・サイトに固有の値を表す。

### 共通の設定（どのアダプタでも必須）

```json
{
  "terms_url": "https://www.city.ohtawara.tochigi.jp/docs/.../",
  "terms_checked_at": "2026-10-27",
  "permission_ref": null,
  "min_interval_secs": 5,
  "contact": "運営者の連絡先（User-Agent に入れる）"
}
```

- `terms_url`・`terms_checked_at` が無い収集先は、`is_enabled` でも動かさない
- robots.txt で不許可の範囲を使うアダプタ（会議録システムなど）は、`permission_ref`（書面の許可の記録。日付と相手先）も必須にする
- 規約を確認した日から1年を過ぎたら、警告を出す（規約の変更に気づくため）

### アダプタ

| adapter | 対象 | 固有の設定 |
|---|---|---|
| `html_link_list` | 一覧ページに PDF のリンクが並ぶ形式（大田原市の予算書など） | 一覧ページの URL、リンクを抜き出す正規表現、表示名から年度を読む正規表現、資料の種類 |
| `soumu_settlement_card` | 総務省の決算カード | 団体コードだけ（`municipalities.id`）。全市町村で共通 |
| `manual_upload` | 許可を得て受け取った資料（会議録など）を運営者が取り込む | 取り込み元の説明、受け取った日 |
| `kaigiroku`（など会議録システムごと） | 会議録検索システム | **書面の許可があるときだけ有効。** テナント名、取得してよい範囲 |

大田原市の予算書の例:

```json
{
  "terms_url": "https://www.city.ohtawara.tochigi.jp/...",
  "terms_checked_at": "2026-10-27",
  "min_interval_secs": 5,
  "list_url": "https://www.city.ohtawara.tochigi.jp/docs/2023051700017/",
  "link_pattern": "\\.pdf$",
  "fiscal_year_pattern": "令和(\\d+)年度",
  "document_type": "budget"
}
```

同じ形式のページを使う自治体は、同じアダプタに設定を足すだけで追加できる。会議録システムは、同じベンダーのシステムを使う自治体が多いので、1つのアダプタで複数の自治体に対応できる（許可は自治体ごとに取る）。

## 取得の共通処理

すべてのアダプタは、共通の取得処理を通して接続する。アダプタが直接 HTTP を使うことはしない。

1. **robots.txt の確認**: サイトごとに取得し（1日キャッシュ）、不許可の URL には接続しない。`permission_ref` がある収集先だけ、許可の範囲で例外にする
2. **間隔**: 1サイトあたり `min_interval_secs`（既定 5 秒）以上あける。並列には取得しない
3. **条件付き取得**: ETag / Last-Modified を保存し、変わっていなければ本文を取得しない
4. **User-Agent**: サービス名と連絡先を入れる（例: `civic-platform-collector/0.1 (+連絡先)`）
5. **大きさの上限**: 1ファイル 100MB まで。超えたら取得をやめて運営者に知らせる

## 変更の検知

- 一覧ページの中身のハッシュで、変化があったときだけリンクを抜き出す
- 資料ごとに URL と本文のハッシュで、新規・更新・変化なしを判定する
- 前回あった資料が一覧から見つからなくなったら、運営者に知らせる（サイトの構成の変更に早く気づくため。このときは自動で設定を直さない）
- 抜き出せたリンクが0件になったら、設定（正規表現など）が古くなったとみなして、その収集先を止めて知らせる

## 抽出（LLM）

- Claude Opus 5.5 を Batch API（半額）で使う。急がないので、即時の応答は要らない
- PDF は文書として渡し、ページ番号つきの引用（citations）を使う。カードの数値には、必ず出典のページを付ける
- 抽出の結果は、数値（事実）・短い引用・出典（URL とページ）だけ。資料の文章をそのまま長く載せない
- 処理が終わったら、原本は捨てる。残すのは次の `documents` だけ
  - `fetch` で取った原本は、`import` までの間だけ `data/private/fetched/<slug>/<対象>/`（git の管理外）に置き、`import` が保存を終えたら消す（`--keep` で残す）。原本の隣の記録（`<名前>.meta.json`）に取得元の URL と条件付き取得の記録を持ち、`fetch_cache` に入れるのは保存が済んだあと（失敗したら次の `fetch` で取り直す）
  - 手でコピーした原本（会議録・PDF）は、運営者が `data/private/` に置き、手で消す

```
documents
  id, collector_source_id, url, sha256, fetched_at, page_count,
  fiscal_year, document_type, etag, last_modified, status
```

- 抽出の結果からトピックのカードを作る。トピックは自動タグ付け（フェーズ4）を通る

## 会議録の手動取り込み（フェーズ5a で実装）

自動取得の許可が出るまで、運営者が手でコピーした会議録を取り込む（ADR 0004）。

1. 会議録を UTF-8 のテキストで `data/private/minutes/` に置く（git の管理外）。会議名・開催日・会議録のページの URL を控える
2. `extract minutes ... --dry-run` で、発言の数・発言者・名簿に無い首長・議員・議事日程を確かめる
3. 名簿に無い人がいれば、`data/seeds/030_officials_*.sql` に登録して `seed` する
4. `extract minutes ...` で AI の出力を作り（API。共同作業なら `--manual`）、`import minutes ...` で下書きを作る。`show topic` で確かめ、`edit topic` などで手直しして `publish topic`

読み取りの形は `collector_sources`（`kind = 'minutes'`、`adapter = 'manual_upload'`）の `config` で自治体ごとに差し替えられる。

| 設定 | 既定 | 意味 |
|---|---|---|
| `speaker_pattern` | `^[○◆◎▲□◇]\s*(?P<role>…)\s*[（(](?P<name>…)[）)]` | 発言の見出し（記号 + 役職（氏名）） |
| `skip_pattern` | `^(△\|（…）$)` | 発言ではない行（節の見出し、ト書き） |
| `agenda_pattern` | `^(追加)?日程第` | 議事日程の行 |
| `topical_agenda_pattern` | `一般質問\|代表質問` | トピックを作る議事。これが無い会議録は取り込まない |

## 総務省の決算カード（フェーズ5b で実装）

`soumu_settlement_card` アダプタ（`backend/src/collect/settlement_card.rs`）。全市町村で同じ設定で動く。

- 規約: 総務省ホームページの「著作権について」（https://www.soumu.go.jp/menu_kyotsuu/policy/tyosaku.html）で、公共データ利用規約（第1.0版）に準拠。出典の記載と、加工したときはその旨の記載が条件（国が作ったように見せない）。画面では「出典：総務省「市町村決算カード」を加工して作成」と、年度のページへのリンクを出す
- robots.txt: `ia_archiver` 以外は制限なし（2026-10-27 確認）
- 形式（2026-10-27 に平成27年度・令和5年度の栃木県の Excel で確認）
  - 決算カードの一覧（`card.html`）→ 年度のページ。ページの番号は規則的でないので、リンクの文字（「令和5年度市町村決算カード」）から年度を読む。Excel があるのは平成27年度以降
  - 年度のページは Shift_JIS。都道府県の欄（`■栃木県`）の `alt="EXCEL"` のリンクが Excel。北海道は複数に分かれている
  - Excel（.xlsx、県で約1MB）は1自治体1シート。シートの名前は年度で違う（「10大田原市」「大田原市」）ので、シートの中の団体コード（「都道府県名」の下の2桁 + 「団体名」の下の4桁 = 6桁）で探す
  - 値の位置は年度で行がずれる。見出しの文字（空白を除き、全角を半角にして比べる）で探し、その右の最初の値を読む。「公債費」「歳出合計」は性質別と目的別の両方にあるので、表の見出し（「目的別歳出の状況」など）の列の近さで区別する
  - 歳入・性質別・目的別は、費目の合計を「歳入合計」「歳出合計」で検算し、合わなければ保存しない（形式が変わったことに気づくため）
  - 人口は「住民基本台帳人口」の下の最初の数値（その年度の1月1日現在）
- 同じ県の Excel を複数の自治体が使うので、条件付き取得の記録（`fetch_cache`）は収集先ごと
- 大田原市の10年分（平成27〜令和6年度）の取り込み: 接続は約21回、約2分。費用なし

## 当初予算の概要（フェーズ5c で実装）

`html_link_list` アダプタ（`backend/src/collect/link_list.rs`）と、AI による抽出（`backend/src/budget/`）。

- **何を見せるか**（ユーザーと決定。2026-10-27）: 今年度の予算の全体（款別・性質別・歳入・1人あたり）、予算と決算の比較、主な事業（名前・金額・新規/拡充・分野タグ）
- **著作権**（法的な助言ではない）: 数字・事業の名前・政策の名前・「どの事業がどの政策か」は事実なので使う。説明の文章・図・レイアウトは市の著作物（15条の職務著作）なので使わず、原本の PDF のそのページへリンクする。政策の体系をそのままの並びで再現するのは、編集著作物（12条）のおそれがあるので避け、画面の並べ方（金額の順・分野タグ）はこちらで決める。PDF からの抽出は 30条の4 の範囲
- **大田原市の規約**: 「著作権法上認められた場合を除き、無断で複製・転用できない」（https://www.city.ohtawara.tochigi.jp/docs/2013092300048/ 、2026-10-27 確認）。公開の範囲は情報政策課に確認中
- **自治体による違い**（2026-10-27、令和8年度の概要を比べた）: 主な事業の分け方は、大田原市が総合計画の政策→施策、那須町が総合計画の分野（新規◎・拡充○）、那須烏山市が基本目標→重点戦略（新規●・拡充○）、那須塩原市が款とテーマの記号。どこにも共通してあるのは、款別・性質別の額と、事業の名前・金額。そのため画面の軸は款と分野タグにし、政策の名前は `budget_projects.plan_label` に持つだけにした
- **設定**: `list_url`（一覧ページ）、`link_pattern`（取り込むリンクの文字の正規表現。大田原市は `^当初予算の概要`）、`from_fiscal_year`（それより前は取り込まない。AI の費用を抑えるため）。年度はリンクの文字の「令和8年度」などから読む
- **抽出**: Claude Opus 5.5 に PDF を渡し、構造化出力で受け取る（引用（citations）は構造化出力と同時に使えないため使わない）
  - 款別は法律で決まった款の名前に合わせさせ、一覧に無い名前があれば区分ごと保存しない
  - 性質別は自治体ごとに分け方が少し違う（那須町は「投資・出資金」と「貸付金」を分ける）ので、決算カードの区分に寄せ、当てはまらなければ「その他」にまとめる
  - 歳入は資料のとおりに読ませ、確かめる処理で決算カードの名前にそろえる（市税 → 地方税、県支出金 → 都道府県支出金、市債 → 地方債など。`budget::revenue_key`）。決算と予算を切り替えても同じ名前で並ぶように。使用料と手数料は、予算の資料が分けていないので「使用料・手数料」にする。対応の無い名前はそのまま残す
  - 新規・拡充の印は、記号のことも文字の色（大田原市は赤）のこともある。主な内容の一部だけが新規なら「拡充」
- **確かめる処理**: 款別・性質別・歳入は、合計が歳出の合計と一致しなければ保存しない。事業は、名前と金額が AI の返したページ（前後1ページまで）の本文（`pdftotext -layout`）にそのまま含まれるものだけを残す。表の中で名前が何行かに折り返されていてもよく（4つのかけらまで）、長音とハイフンの類い（ー・－ など）は同じ文字とみなす
- **原本は保持しない**: `fetch budget` で取った PDF は、`import budget` が保存を終えたら置き場から消す。`pdftotext` で読むときは一時ファイルに書き、すぐに消す。DB には出典（URL・ハッシュ）と数字・事業の名前だけを残す
- **実物での結果**（令和8年度）: 大田原市は3区分とも検算が通り、事業165件（新規3・拡充6。ページの画像で確認）、約 0.8 ドル・2分半。那須町は3区分と事業56件中56件が通った（約 0.36 ドル）。那須烏山市（性質別の「投資・出資金」「貸付金」を寄せた）は3区分と事業148件中148件が通った（約 0.57 ドル）。大田原市の令和6年度は事業163件（重複の4件を除いたあと）（新規5・拡充11。ページの画像で一部を確認）、約 0.87 ドル
  - 大田原市の概要は、後ろのページで重点事業を1件ずつ説明している。AI がそこからも事業を少し違う名前で拾うことがある（令和6年度で4件）。金額が同じで分野タグが重なる事業は、先に出たほうだけを残す（金額が同じでも分野が違えば別の事業として残す）
- **費用の歯止め**: 抽出の1日の上限（`LLM_EXTRACTION_DAILY_BUDGET_USD`、既定5ドル）に達すると呼ばない。AI を呼ぶのは `extract` だけ（`fetch` と `import` は呼ばない）

## AI の作業の2つの道（API と共同作業）

（docs/plans/2026-10-28-manual-extraction.md。2026-10-28 ユーザーと決定）

- 会議録・予算の概要を AI に読ませる作業は、**API で呼ぶ**か、**運営者が Claude Code などとの共同作業で出力を作る**（`extract ... --manual` → JSON → `import`）かを選べる。決算カードは AI を使わない
- どちらの出力も、同じ検査（`minutes::extract::check`・`budget::check`）を通る。共同作業でも、作られるのは下書きで、運営者が確かめてから公開する（ADR 0004）
- 取り込みは年に数回なので、自治体の数が少ないうちは共同作業を基本にする（費用は契約の範囲で追加なし。手間は1日分で10〜20分ほど増えるが、いちばん重いのは下書きの確認で、どちらでも同じ）。自治体が増えて定期の実行にしたくなったら、API の道を使う
- **投稿のモデレーションは API のまま**（市民の投稿をその場で判定するので、人を介せない。API キーが無いと全件承認になるので、本番では要る）
- どちらで作ったかは `documents.extraction`（`api` / `manual`）に残す

## 公人と発言者（会議録）

- 公人の表（例: `public_officials`）: 氏名、役職（首長・議員など）、自治体、任期の開始・終了。改選・辞職・補欠選挙は任期で表し、過去の記録との対応を保つ
- **発言と人物の対応は、会議録の発言者の記載（「○3番（〇〇議員）」など）から機械的に決める。** LLM に人物を推測させない（取り違えると、実在の人に言っていないことを結び付けることになり、名誉毀損のおそれがある）。対応が取れない発言は人物に結び付けない
- 記録には出典（会議名・日付・URL・ページ）を必ず付ける
- トピックのカードでは、「背景・出典」の欄に「〇〇議員（〇年〇月 定例会）」と引用つきで示す
- **投票の対象になる意見（statements）の文には議員名を入れない。** 「誰の意見か」ではなく中身で賛否を付けてもらうため（Polis の原則、ADR 0002 と同じ考え方）
- 議員名はタグにしない（ADR 0003）

## 規模の見積もり（1自治体・1年あたり）

| 項目 | 見積もり | 根拠 |
|---|---|---|
| ダウンロード | 約 60MB | 予算関係は約 55MB（大田原市の実測）。会議録は許可を得てから実測する |
| 保存 | 1MB 未満 | 原本を保持しないため。`documents` と抽出の結果だけ |
| LLM の入力 | 約 400 万トークン | 推定。予算書の PDF が大半 |
| LLM の費用 | 約 1,300 円 | Opus 5.5 の Batch。評価のあとで見直す |
| 日々の更新の確認 | 数十 KB | 一覧ページの条件付き取得だけ |

## 1台のサーバーで扱う自治体の数

データの量（1自治体で年 60MB の転送、保存 1MB 未満）も、LLM の費用（年 1,300 円程度）も小さく、技術的には数百の自治体でも1台で扱える。

制約になるのは**運営者の手間**（許可の取り付け、規約の確認、サイトの変更に合わせたアダプタの保守）である。そこで、次のように進める。

1. 大田原市で、予算書・決算カード・手動取り込みの会議録を一通り動かす
2. 栃木県内で、同じ会議録システム・似たサイト構成の自治体から増やす
3. 1台で**50自治体程度まで**とする。それを超えるときは、PostgreSQL への移行と、収集処理を別のサーバーに分けることを検討する
