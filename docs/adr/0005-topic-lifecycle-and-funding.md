# ADR 0005: トピックの寿命・投稿数・資金・提言

- 状態: 承認（一部改訂 2026-10-28・2026-10-29。「提言の作り方」と「下書きの確認の手間」は検討中）
- 日付: 2026-10-27（改訂 2026-10-28・2026-10-29）
- 計画: `docs/plans/2026-10-27-adr-0005-policies.md`、改訂は `docs/plans/2026-10-28-adr-0005-revision.md`・`docs/plans/2026-10-29-analysis-unlock-seeds.md`
- 関連: ADR 0002（市民を分けて見せない）、ADR 0003（LLM の運用）、ADR 0004（会議録の扱い）、`docs/polis-math.md`

## 背景

- 会議録から作ったトピックは、時間がたつと今の状況を表さなくなる（議決された、事業が始まった、など）
- 意見の数が多すぎると、全部に投票できなくなる。このアプリは「そのトピックの全部の意見に投票するまで分析を見せない」ので、意見の数の影響がとくに大きい
- 運営の費用は、寄付・投げ銭でまかなう方針。行政からの出資は、公平性の観点から受けない。お金の出し方によって議論への影響が変わると、「1人1票」と「分断を生まない」（ADR 0002）の原則に反する
- 合意点の安定したトピックを、似たもの同士でまとめ、行政への提言やさらなる議論につなげたい

## 決定

### トピックは期限つき

- 投票の期限の既定は、公開から90日。議決や事業の開始などで状況が変わったら、運営者が早めに締め切れる
- 締め切ったトピックも、結果（意見マップ・グループ・合意点）は読める。止めるのは投票と投稿だけ
- 会議録から作ったトピックは、議論のあった日（会議の日）を目立たせて出す。古い議論だと分かるようにするため

### 投稿数の上限（2026-10-28 改訂）

- **意見は、参加する人は1トピック1件まで**（承認待ち・確認待ちを含む）
- **市民提案のトピックでは、提案した本人だけ3件まで**。議論のたたき台を示し、合意を探る動機を持ってもらうため
- 議会のトピックは、議会での主張が最初の意見になっている（ADR 0004）ので、運営者や提案者の分は要らない
- 市民からのトピックは「提案」として受け付け、運営者の確認を通ったものだけを公開する。提案は1人あたり、1つの自治体に週1件まで（2026-10-29 に自治体ごとと決めた）
- 上限は1人を見分けられて初めて意味があるので、実装はフェーズ6（認証）と一緒にする
- 改訂の前は「1人1トピック3件まで」だった。会議録からトピックを自動で作ってみると、議会のトピックだけでも数が多くなると分かり、見直した

### 似た意見は、公開せずに案内する（2026-10-28 追加）

- 投稿のとき、AI がそのトピックの公開済みの意見と比べる。**同じ立場で同じことを言っている**意見があれば、公開せず、その意見を示して「こちらに投票してください」と案内する
- 案内した投稿は、上限の1件に数えない（言い直して、別の意見として出し直せる）
- 立場が逆のもの、言いたいことが少しでも違うものは、別の意見として通す。似ているかどうかだけを見て、主張の中身や立場では判断しない（モデレーションの原則と同じ。ADR 0003）
- AI が判定できないとき（通信の失敗・費用の上限）は、重複ではないとみなして通常のモデレーションに進む
- 理由: Polis 本家も、重複した意見はモデレーションで外すよう勧めている（[Moderation](https://compdemocracy.org/Moderation)）。同じ意見が並ぶと、投票の手間が増えるだけで、分析にも偏りが出る

### 分析は、最初の意見すべてに投票したら見られる（2026-10-29 改訂）

- **最初の意見（議会での主張など。`statements.is_seed`）すべてに投票したら、分析を見られる。意見を投稿できるのも同じ条件**（ほかに、パスキーの登録と上限の1件）
- 全体の傾向を見る前に自分の考えで投票してもらう、という目的は、議会での主張への投票で保つ。最初の意見はどの参加者にも同じなので、条件が人によってぶれない
- 公開中のトピックに足す意見は最初の意見にならない（下の「会議録から作るトピック」）ので、公開したあとに一度開いた分析は閉じない
- 最初の意見が少ないトピックは、公開の前に運営者が確かめる（下限は設けない）。最初の意見が無いトピックは、すぐに開く
- 残りの意見は、Polis の優先度（見た人の少ない新しい意見を多めに出す）の順に、引き続き投票できる
- **意見を投稿したら、書いた人はその意見に賛成したものとする**（Polis と同じ）。自分の意見に投票を求められず、書いた人の立場が意見マップに入る。非公開になった意見と、似た意見として案内した投稿（保存しない）には入れない
- 経緯
  - 最初は「そのトピックのすべての承認済みの意見に投票するまで、分析を見せない」だった。1人あたりの上限ではトピックの意見の総数は抑えられず（参加者が100人なら、1人1件でも100件になる）、意見が多いトピックでは分析までの道のりが長くなりすぎる。Polis 本家も、全部への投票は求めない
  - 2026-10-28 に「最初の意見すべてと、合わせて15件（意見がそれより少なければ全部）」にした。動作確認で、意見が15件より少ないトピックでは、自分や他の人の意見が増えるたびに分析が閉じ、投票すると開く、を繰り返すと分かり、2026-10-29 に今の形にした
  - 「すべての意見に投票したら投稿できる」も検討したが、採らなかった。意見は参加者に比例して増えるので後から来た人ほど投稿までの投票が増え（参加の時期で決まりが変わる）、他の人の意見が承認されるたびに条件が揺れて書いている途中で投稿できなくなり、投稿のためのパスの連打が分析を濁らせる。同じ意見の重なりは、似た意見の案内で防げる

### お金で議論への影響を変えない

- 寄付・投げ銭の有無や額で、投稿数・投票・表示の順番など、議論に関わるものを変えない
- 支援者への特典は、議論の外のものに限る。支援者の名前の掲載（本人が同意したときだけ）や、収支の報告など。名前は意見とは結び付けない（匿名性、CLAUDE.md）
- 収支は公開する（行政の透明性を掲げるサービス自身も透明にする。ライセンスの方針と同じ考え方）
- 次の寄付・出資は受けない
  - 行政からの出資（公平性のため）
  - 政党・政治団体・候補者からの寄付（特定の立場との結び付きを疑われないため）

### トピックの統合は「提言」と「第2回のトピック」の順に作る

- 投票はトピックをまたいで混ぜない。意見の集合が違うと、Polis の分析（PCA・クラスタリング）が成り立たないため
- **提言**: 似たトピックの合意点などを集めたページ。印刷・PDF にでき、陳情・パブリックコメント・市長への手紙などに使える形にする
- **第2回のトピック**: 提言の中身を最初の意見にした新しいトピック。新しく参加する人にも投票してもらう
  - 元の提言へのリンクを付け、どんなトピックが積み上がってきたかをさかのぼれるようにする

### 会議録から作るトピックが、既存のトピックと同じ論点のとき（2026-10-28 追加）

- **同じ論点の基準**: 同じ自治体で「何を決める・変えるか」が同じもの。賛成・反対のどちらの立場で語られているかや、言い回しでは判断しない（似た意見・タグの基準と同じ考え方）
- 取り込みのとき、AI（または共同作業）に、その自治体の公開中・下書きのトピックの一覧を渡し、同じ論点なら印（`same_as`）を付けてもらう。印を付けるかは運営者が下書きの確認で確かめる
- **印の先が下書き**（同じ定例会の別の日など）: 1つの下書きにまとめる。意見は最初の意見として、出典の引用も足す
- **印の先が公開中のトピック**: 新しいトピックは作らない。既存の意見に無い議会の主張だけを、確認待ち（flagged）で足し、運営者が採否を決める。**最初の意見としては扱わない**（`statements.is_seed = false`）。公開中の画面の出典の引用は、運営者の確認を経ずに変えない
- **印の先が締め切ったトピック**: 新しいトピックとして作り、前のトピックへのリンクを付ける（締め切ったトピックができたら作る）
- **1日分の会議録から作るトピックの数**: 上限を5件から15件に広げる。公の会議で論じられたものはできるだけ取りこぼさず、すべて下書きにして運営者の承認を待つ。論題の幅と確認の手間はトレードオフだが、幅を優先する（2026-10-28）
  - 公開をまとめて行うと、ユーザーが日々関心を払ってくれにくい。下書きを少しずつ公開し、タイムラインに日々議題が上がるようにする（公開のペースの作り方は、後のフェーズで計画する）
- **最初の意見が少ないトピック**（3件未満）: 捨てずに下書きとして残し、運営者の承認を待つ。立場が偏っていないかは運営者が確かめる
  - 反対の立場の意見を AI で作る案は採らない。ADR 0004 の「AI に新しい選択肢を作らせない」とぶつかり、改修も増えるため。足りない立場は、参加する市民が足していく
- **類似度の判定のしかた**（ベクトル検索など）は、後のフェーズの「意見の取りまとめ」（提言の似たトピックの選び方を含む）で、トピックと意見の両方について決める。それまでは一覧との読み比べだけにする

## 会議録のトピックの下書きの確認の手間（検討中）

会議録から自動でトピックを作ると、1日分で5件前後の下書きができ、運営者が1件ずつ確かめるのは負担が大きい。
下書きの確認そのもの（ADR 0004。要約の誤りや発言者の取り違えをそのまま出さないため）はやめない。次の案を検討する。

- ~~1日分の会議録から作るトピックを、最大3件に絞る~~（採らない。上の「1日分の会議録から作るトピックの数」のとおり、取りこぼさないことを優先する。2026-10-28）
- 下書きをまとめて確かめる CLI を作る。一覧で、タイトル・最初の意見・出典を並べ、採否だけを決められるようにする

## 提言の作り方（検討中）

ユーザーと詰める案。決まったらこの節を書き直す。

### 提言にしてよいトピック（合意点が安定したか）

- 締め切ったトピック、または、分析の対象が30人以上いるトピック
- 意見のグループが2つ以上ある
- 合意点の顔ぶれが、直近2週間の分析で変わっていない
  - 判定は、合意点の集合の重なり（ジャカード係数）が 0.8 以上
  - そのために、分析の結果の履歴を残す

### 似たトピックの選び方

- 同じ分野タグを持つトピックの中から、AI が「同じ論点を扱っているもの」の候補を出す
- まとめるかどうかは運営者が決める。AI は候補を出すだけ

### 中身は数理とプログラムで決める（AI に文を作らせない）

- **合意点**: どのグループでも8割以上が賛成した意見。今の判定（`(A+1)/(S+2) ≥ 0.8`）を使う
- **意見が分かれた点**: あるグループでは多くが賛成し、別のグループでは多くが反対した意見。合意点だけを並べると、議論の全体が伝わらないため
- 意見の文は**原文のまま**載せる。それぞれに、元のトピック・参加した人数・賛成の割合を添える
- 関わり方の内訳（二次秘匿済み。ADR 0002）、期間、元のトピックへのリンクも載せる
- AI が書いてよいのは、中立な見出しと短い前書きだけ。これも下書きにし、運営者が確かめてから公開する（ADR 0004 の下書きと同じ）

### 提言を、別の提言にまとめてよいか

- まとめてよい。ただし、下の提言の文章（見出しや前書き）はまとめに使わない。その元になった意見（原文と数字）をたどって集める
  - 要約の要約を重ねると、もとの投票から離れていくのを防ぐため
- 提言のつながりは木の形でたどれるようにし、循環は作れないようにする

## 理由

- 期限は、古い議論が今の意見のように見えることを防ぐ。締め切っても結果を残すことで、記録としての価値は保つ
- 投稿数の上限は、全部に投票してから分析を見る、という作りと両立させるため
- お金と議論への影響を切り離すことで、資金の出し手によって合意点が動くことを防ぐ
- 提言の中身を数理と原文に限ることで、AI や運営者が結論を作ってしまうことを防ぐ

## 影響

- `topics` に、投票の期限と締め切りの状態が要る（`status` の 'closed'、`closes_at` など）。意見の上限は投稿の API で確かめる。市民提案のトピックには、提案した人の記録が要る（画面には出さない。匿名性）
- 似た意見の案内には、投稿の判定の結果に「重複」を足す（公開しない。案内する意見の ID を返す）
- 分析のロック（`/analysis` の `locked`）は、「最初の意見すべて」で判定する
- 提言には、分析の結果の履歴、提言と元のトピックのつながり、提言どうしのつながりのテーブルが要る
- 寄付の受け付けの仕組み（外部のサービス）と収支の公開の方法は、フェーズ7（リリース準備）で選ぶ
- 2026-10-28（フェーズ6b）: 投稿の上限・分析を開く条件・投稿できる条件（分析を見られてから）は `backend/src/process/progress.rs`、似た意見の案内は意見の審査（ADR 0007、`backend/src/process/moderation.rs`）で実装した。市民提案のトピックの3件は 6d、トピックの期限と締め切りは 6c
- 2026-10-29: 分析と投稿を開く条件を最初の意見すべてにし（`Progress::analysis_remaining`）、投稿した人の賛成の票を投稿の API（`backend/src/interface/api/participation.rs` の `post_statement`）で入れる
- 2026-10-29（フェーズ6c）: 期限は `topics.closes_at` で持ち、過ぎたかで締め切りを決める（`status` に 'closed' は足さない。期限で自然に締め切れ、定期の処理が要らないため）。公開したときに `published_at` と90日後の `closes_at` を付ける。それより前に公開したトピックは期限なし（NULL）。運営者が早めに締め切るときは、管理画面で `closes_at` を今にする。締め切ったトピックの分析は、投票していない人にも見せる（ロックは投票が全体の傾向に左右されないためのもので、投票が終われば理由がない）。ルールは `backend/src/process/progress.rs`
- 2026-10-29（フェーズ6d）: 提案は「タイトル・説明（140字以内。議会のトピックと同じ長さで、本人が書く。AI でまとめ直さない）・最初の意見1〜3件」。下書き（`source_type = 'citizen'`）として保存し、提案した人は `topics.proposed_by` に持つ（API のどこにも返さない。運営者の API でも）。提案した本人の3件には、提案に含めた最初の意見も数える。本人の賛成の票は公開したときに入れる（提出のときに入れると、運営者が意見を直せなくなるため）。提出のときは公人の氏名だけをプログラムで確かめ、AI の審査は呼ばない（運営者が全件を見る）。結果は本人だけが「自分の提案」で見る（確認中・公開・見送り。理由は出さない）。週1件は見送りになった提案も数える。ルールは `backend/src/process/progress.rs` の `propose_permission`・`post_permission`。計画は `docs/plans/2026-10-29-phase6d-citizen-proposals.md`
