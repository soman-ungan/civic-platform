# ADR 0009: 資料は手元でデータ化し、本番は検査と保存だけにする

- 状態: 承認（2026-11-21）
- 計画: `docs/plans/2026-11-21-local-ingest-ops.md`
- 関連: ADR 0003（AI の運用）、ADR 0004（会議録）、`docs/design/collection.md`（収集）、`docs/operations/deploy.md`（資料を本番に入れる）

## 背景

当初の構想（`docs/grand-design.md`・フェーズ5）では、本番のサーバーが行政資料を集めて Claude API で読み、取り込みを定期的に回すつもりだった。
公開（2026-11-10）からの実際の運用は次のとおりで、こちらのほうが管理しやすいとユーザーが判断した。

- 会議録・予算の概要は、手元で運営者と Claude Code の共同作業（`extract --manual`）で JSON にする。API の費用がかからず、運営者がその場で中身を確かめられる
- `deploy/upload.sh` で原本と JSON を本番に送り、本番の `import` が検査して下書きにする
- 会議録の指示文は本番で作る（`upload.sh --prompt`）。本番の既存のトピックが指示文に入り、同じ論点の統合（`same_as`）が本番に対して効く
- 会議録は市のサイトの規約のため自動では取れない（手でコピー）。予算と決算は年に1回

## 決定

1. **資料のデータ化は手元で行う。** 会議録・予算の概要を AI で読むのは、手元の共同作業（`--manual`）か、手元で API を呼ぶ `extract` だけ
2. **本番は検査と保存だけ。** 本番の DB に資料を書く窓口は、本番の `import` 1つ。引用が原文にあるか・氏名・合計の検算・AI の審査などの検査は、本番でもう一度通る（手元の検査を信用しない）
3. **本番では API で資料を読まない。** 本番（パスキーのドメインが localhost でない。`Config::is_production`）では、`extract` は `--manual`（指示文を作る）と `--dry-run` だけが動き、API を呼ぶものはエラーで止まる。本番の設定から抽出のモデルと費用の上限を外す
4. **定期の収集はしない。** 「公開のあとに回したもの」にあった収集の定期実行は、予定から外す。決算カードは AI を使わない決まった処理なので、これまでどおり本番のサーバーが総務省から取る（`fetch settlement` → `import settlement`）
5. 手元の DB（`data/civic.db`）は開発と試しのためのもので、本番とは別物。取り込みの手順書（`.claude/commands/`）は本番を本筋にする

## 理由

- 本番に書き込む経路を1つにし、検査をそこで必ず通すと、手元で何を使って作っても本番のデータの質が保たれる
- 本番にも API キーがある（意見の審査に使う）ので、`extract` を本番で動かせると、うっかり費用がかかる
- 共同作業のほうが、抽出の中身（トピックの切り方・統合・引用）を運営者がその場で直せる。ワンオペでは、自動で回すより確かめながら入れるほうが事故が少ない

## 影響

- コード: `extract` の入口で本番を止める（`interface/cli/ingest.rs`）。API で読む処理（`Extraction::Api`）は手元のために残す
- 運用: 本番のコマンドは `deploy/prod.sh`（`docker compose exec` の薄いラッパー）。AI の利用は `list usage` で見る
- ADR 0003 の「行政資料の抽出（フェーズ5）」は、手元だけの使い方になる
